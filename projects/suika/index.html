Teaching a neural network to play Suika Game

The game

In Suika, fruit drop into a box one at a time. When two of the same fruit touch, they merge into the next size up: cherries become strawberries, and so on up to melons and watermelons. If the pile reaches the top, the game is over.

Merging two watermelons clears them from the board. Building that pair takes planning: smaller fruit can block the merges needed to reach it. I focused on how often the bot could achieve this and whether it could keep playing afterwards.

How it works

  1. A reproducible game engine. I built a Rust version of the game based on Matter.js physics. A deterministic engine lets me replay games from the same seed and compare candidate moves under the same conditions. The browser demonstration runs that engine through WebAssembly.
  2. Search possible moves. For each move, the bot simulates about 32 drop positions. For the four most promising positions, it also considers the next fruit. In the real-time version, it chooses when to drop as well, allowing it to act while the pile is still moving.
  3. Evaluate the board. A small, three-layer transformer represents each fruit as a token and uses the geometry between fruit to help predict how long the game will survive. That estimate helps the search choose between possible moves.
  4. Learn from self-play. The network trains on games generated by the bot, using TD(λ) to update its predictions from later outcomes. Training also restarts from difficult saved positions and constructed endgames, giving the network more practice with situations that occur rarely in full games.

Profiling helped reduce the cost of these experiments. A fused attention kernel and scheduling simulation work per drop made evaluation about four times faster and training about 1.75 times faster in the benchmark runs, while preserving the bot's decisions.

Results

What I learned

1. Small numerical differences can change decisions

The network's final layer used 16-bit floating point. Around the values it produced, rounding steps of about 0.016 could erase differences between candidate moves. Ties were then broken in favour of the leftmost drop. Running that layer in 32-bit increased the double-watermelon success rate from 36.0% to 40.2% across 768 evaluation games, without retraining.

2. Drop timing changes the strategy

Under the real-time rule the bot can drop before the pile settles. To check the gain wasn't simply from weighing more options, I ran a control: turn-based play with 128 drop spots, about as many options as real-time's 32 spots times 4 timings. The control reached 27.1%; real-time play reached 44.8% with the same network. This suggests that choosing when to drop helped beyond simply trying more positions. A fresh set of evaluation games also favoured the real-time version (30% vs 45%). The bot ended up dropping into a moving pile in 59% of its moves.

3. Small evaluations can be misleading

With 192 evaluation games and a success rate near 50%, a 95% confidence interval spans roughly seven percentage points on either side. Small differences between runs therefore need more evidence. I used larger evaluations of 576 or more games for closer comparisons and reported Wilson confidence intervals alongside the success rates.

What's next

  • Train with the real-time dropping rule from the start.
  • Test how long the bot can continue after clearing a pair of watermelons, using a longer planning horizon and practice from positions just after a clear.
  • Test whether a larger network improves play enough to justify the extra computation.
